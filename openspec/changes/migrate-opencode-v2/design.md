# Design

## Context

See proposal.md. The current V2 SDK is 2.1.3; its host uses OpenTUI 0.6.6. Official contracts were checked in the published SDK/client and tagged host sources, including command dispatch, composer handling and plugin storage.

## Goals / Non-Goals

Preserve the existing sidebar feature set and OpenSpec flow while using V2 APIs directly. Do not introduce a V1-shaped compatibility facade or introspect host renderables to modify its composer.

## Decisions

1. Export `Plugin.define({ id: "openspec-tui", setup })` and append to `sidebar.content`. Use the slot session ID and session location; remount on session/location changes so selections, requests and timers do not leak between projects. Keep the single poll in the root. Read files using explicit location and decode bytes with TextDecoder.
2. Register `/opsx-config` and `/opsx-baseline` through `keymap.layer` with `slash.arguments: true`. V2 invokes handlers with the argument string. Running sessions are gated at execution. The host owns layer disposal.
3. The V2 public context has no prompt append API. Former draft-only actions open `ui.dialog.prompt`; Enter submits the edited text and Escape cancels. Capture the intended session before awaiting the dialog, then reject if the route changed or the session became running. Resolve OpenSpec slash commands to their configured template and submit expanded text through `client.session.prompt`; ordinary text uses the same API. Resolve before any session mutation and recheck route/location/running state afterwards. Read ordered sources with `client.config.get` at the captured project location, taking the last matching document command or markdown command (`commands` after `command`). Read project markdown through the server at the captured project location with a project-relative path, preserving links to templates elsewhere in that project. Use the source configuration directory for external/global sources. Select POSIX or Windows path semantics from the server path, never from the TUI OS. Do not widen reads to the filesystem root. Preserve `$ARGUMENTS`, numbered/quoted arguments and appended arguments. Parse markdown using gray-matter with OpenCode 2.1.3's colon-sanitizing retry and validate command fields before choosing a definition. Skip invalid YAML/metadata, continuing to the next native source; never submit the invalid body. Use valid metadata only for definition validation, ignoring agent/model/subagent/subtask values at execution. Bundle gray-matter 4.0.3 and reject its executable JavaScript frontmatter engine: metadata must remain data in the TUI. Reject missing, unreadable, empty or shell-interpolated templates with actionable feedback and no native fallback. Do not register temporary commands or rewrite configuration. Keep the user's main draft intact. On home, create a session at the current location, then navigate to it. Explore selects Plan; all other plugin agent actions select Build. Capture the user-selected model and variant before the dialog, show these settings, and use the same captured selection for execution. If editing changes the required agent, reopen the dialog with the new settings before submission. Cancellation never switches session settings. Without a selected model, show guidance and send nothing. For existing sessions, await switchAgent then switchModel before dispatch, rechecking the captured route/location and running state after each await. New sessions receive the explicit agent and model at creation. Do not restore the old agent while the turn is executing. Prevent duplicate pending submissions per context and surface errors with a toast.
4. Exit through deferred `keymap.dispatch("app.exit")` after the click/render cycle. Do not submit the literal word `exit` as a model message.
5. Map V2 colors into the small component theme model. Use `hue.interactive[200]` for primary/secondary controls and `hue.accent[200]` for accents: action text tokens describe foregrounds on native action surfaces and may be neutral even in colored themes. Keep feedback, ordinary/muted text, background and border semantic tokens, and retain muted disabled controls. Resolve palette values live so theme changes update the existing view. Use OpenTUI types directly. Preserve the current task, spec and search layout; explicitly describe the new dialog behavior in the UI/docs.
6. Replace V1 kv with `storage.store("version-history", { initial: { last: null } })`. Storage is synchronously hydrated by the host and its writes are asynchronous. Config update flags retain priority. A fresh V2 storage record does not invent a V1 version; migration flags still carry known source versions.
7. Reload native command/skill catalogs after init via `client.location.reload`, then repoll. This replaces ephemeral command registration, so no module-global registration set survives plugin reload or changes projects.
8. Configure CLI-only loading with the global `cli.json` / `plugins`, honoring XDG/config-directory and inline overrides. Local TUI plugins require a package directory with a physical `tui.js` entrypoint, not a direct JS file (npm packages use their `./tui` export), preserving string and object entries/options. Documentation keeps the V1 setup/usage guide in docs/v1.md, links it from README, and tells V1 users to keep 1.0.0 and V2 users to use 2.x. Build leaves `@opencode/*`, OpenTUI and Solid external; no duplicate renderer is bundled.
9. Reserve a sidebar-owned submission gate before setup/update preparation, separate from the host's running status. Keep it through the request promise, and reject repeated or competing actions before they can touch completion flags. The accepted operation alone clears its flags on submission failure. Only an actual host running-to-idle transition completes setup, requests reload or records migration history.

## Risks / Trade-offs

- Derivation execution is chosen before Scan, independently of depth: parent only, one child or up to two (recommended), with an explicitly entered positive integer allowed. No child is launched before consent. The same maximum covers Scan, Detail and any verification delegation, including live background children; wait for each bounded batch before starting the next, prohibit nested delegation, and retain one-area-at-a-time verification. Missing tools or a missing/invalid/cancelled answer fall back to parent-only sequential work. Do not persist a machine resource choice in project configuration. This is prompt-level scheduling, not a host-enforced concurrency limit; the pinned TUI context exposes no scheduler hook.
- Keep the overview compact by leaving edit/run and agent/model guidance inside the command dialog. In Settings, a single component update uses its own button; Update All is offered only for two updates. Other setup/error/progress messages remain conditional on their existing states.

- Direct V2 session submission differs from editing the host composer → an explicit editable dialog replaces insertion; tests cover cancellation, busy transitions, route changes and visible errors.
- The plugin cannot read or set the composer's draft agent through the public API → agent policy belongs to the action, is shown in the dialog, and is committed through session APIs. The main composer draft is preserved; the session agent is not automatically restored. OpenCode 2.1.3 `session.command` has no execution overrides and applies native metadata after session selection. Plugin actions therefore use only configured template text and supported argument expansion. Shell interpolation and opaque backend-only command definitions cannot be executed through this path; show guidance instead of dispatching with incorrect settings. Commands typed directly into the host composer retain native behavior.
- File access may be remote → server reads use the session location; local writes retain guarded filesystem access and agent fallback.
- V1 kv cannot be read through V2 → preserve on-disk update flags and initialize V2 storage without fabricating history.
- SDK and renderer changes → typecheck against pinned packages, retain all rendering tests, and smoke-test an isolated actual V2 host without a provider.

## Migration Plan

V1 remains recoverable at local `v1.0.0`. Change package version to 2.0.0, install pinned V2 development packages, adapt APIs/tests/docs, and run all checks plus an isolated CLI smoke. Keep V2 uncommitted and unpublished. Main specs and active V1 deltas remain untouched; sync/archive is a separate operation.
